## 中

### M1　`/health` 与 `/ask` 共用 40 线程池，负载下健康检查超时　— 已修复（`cba550f`）
- 位置：`src/rag_agent/main.py:249`（原为同步 `def health`）；`Dockerfile:19-20`（HEALTHCHECK `--timeout=3s`）。
- 问题：同步端点在 anyio 默认 40 线程池执行，`/ask` 要等模型数秒到数分钟。线程池占满后 `/health` 排队。
- 复现（已实测）：起 uvicorn，假模型每次 sleep 4s，并发 60 个 `/ask`，再请求 `/health`：**3.5 s 后才返回**（空闲时约 0 s），超过 3 s 的 HEALTHCHECK 超时，容器会被标 unhealthy 并（配合编排器）被重启，进而丢掉所有进程内会话。
- 修复：`/health` 改 `async def`，不进线程池。测试：`test_health_does_not_wait_for_the_worker_thread_pool`（结构性断言；行为证据见上）。
- 残余：见 M4（线程池本身仍可被占满，`/ask` 会排队）。

### M2　用假 token 即可占满并挤出他人会话　— 部分修复（`7331b51`）
- 位置：`src/rag_agent/main.py:185-205`（`prepare` 在 KB 校验 token **之前**调用 `sessions.create`）；`src/rag_agent/sessions.py:62-70`（满额时淘汰最旧）。
- 问题：服务本身不验证 token，验证发生在后面的 KB 调用。`remember=true` + 任意 `Bearer x` 会先创建会话；KB 回 401 后会话仍留到 TTL（30 分钟）。1000 个请求即可把真实用户的会话全部淘汰（无需任何有效凭据）。
- 复现（修复前实测）：`Bearer bogus` + `remember:true` → 401，`len(app.state.sessions) == 1`。
- 修复：本请求新建的会话，在 KB 拒绝 token（401），或 `/ask` 以无 session_id 的错误返回时删除。测试：`test_a_token_the_knowledge_base_rejects_leaves_no_session_behind`、`..._does_not_discard_a_session_that_already_existed`。
- **残余（未修复，需设计取舍）**：创建与淘汰仍发生在校验之前，并发洪泛仍能在回收前淘汰少量真实会话；持有效 token 的用户也可独占全部 1000 个槽位。建议：按 owner 限额（例如每 owner ≤ N 个，先淘汰自己的），并把创建推迟到 KB 首次调用成功之后（会改变流式 `session` 事件"最先发出"的次序，故未动）。

### M3　请求体无大小上限，先整体缓冲解析再校验字段　— 已修复（`a29541e`）
- 位置：`src/rag_agent/main.py:103`（新增 `BodyLimit`）；字段上限只在 `AskRequest`（`main.py:30`）里，且发生在解析之后；uvicorn/FastAPI 默认不限制体积。
- 问题 / 复现（已实测）：未认证请求发送 20 MB JSON 到 `/ask`，被完整读入并解析，最后才返回 422。
- 修复：纯 ASGI 中间件，先看 `Content-Length`，chunked 则边收边计数；超限返回 413 `{"error":"request_too_large"}`。默认 64 KiB，`RAG_AGENT_MAX_BODY_BYTES` 可调（2000 字问题即使全部转义为 `\uXXXX` 也只有约 12 KB）。已用真实 uvicorn 验证 Content-Length 与 chunked 两条路径。测试：`test_an_oversized_body_is_rejected_before_it_is_parsed`。

### M4　无并发/速率限制；流式断连不会取消后台工作　— 仅记录
- 位置：`src/rag_agent/main.py:290-322`（无界 `queue.Queue` + 每个流一个 `daemon` 线程）；`main.py:~215` `execute`。README 已声明"无限流、未做压测"。
- 问题：（1）M1 的实测同时证明：约 40 个并发慢请求就能占满线程池，其余请求排队；（2）**疑似**：客户端断开后 `stream()` 生成器所在线程仍阻塞在 `events.get()`，`work()` 线程继续跑完全部模型轮次与工具调用（上限约 `max_turns × llm_timeout + max_tool_calls × request_timeout`，默认最坏 10 分钟以上），期间 KB 连接与模型算力被无用占用。
- 验证方法（断连部分）：假模型每轮 sleep 5s，用 `httpx.stream` 读到第一个事件即关闭连接，随后统计假模型被调用次数是否仍达到 `max_turns`。
- 建议：反向代理/网关层做限流与连接数限制；服务内加全局信号量（429）和断连检测（`request.is_disconnected()` 轮询 + 取消标志，在每轮模型/工具调用之间检查）。涉及行为与超时语义取舍，未改。

## 低

### L1　含非 ASCII/控制字符的 token 导致 HTTP 500　— 已修复（`67fd01d`）
- 位置：`src/rag_agent/main.py:65-77`、`src/rag_agent/mcp_client.py:129`（header 构造）。
- 问题：Starlette 以 latin-1 解码请求头，`Bearer café` 取到 `café`；httpx 以 ASCII 编码头值，抛 `UnicodeEncodeError`（不是 `McpError`），`/ask` 返回 500；流式路径变成 `internal_error` 事件并写一条带 traceback 的日志。已复现：`McpClient(..., "caf\xe9").list_tools()` 抛 `UnicodeEncodeError`。
- 修复：`bearer_token` 对非"可打印 ASCII 且无空格"的值按未认证处理（401）。真实 token（JWT/随机串）不受影响。测试：`test_a_token_that_cannot_be_a_header_value_is_unauthorized_not_a_crash`。

### L2　模型服务返回畸形 JSON 时 500 而非 502　— 已修复（`3a7f0a6`）
- 位置：`src/rag_agent/llm.py:90`（`complete_stream`）、`:172`（`complete`）。
- 问题（已复现）：`{"choices":[{"message":"x"}]}` → `AttributeError`；流式 chunk 为 `[1]`、`choices:["x"]` 或 `tool_calls[].index="x"` → `AttributeError`/`ValueError`。这些不是 `LlmError`，`run_agent` 不会转成 `model_error`，`/ask` 500。
- 修复：形状校验后统一抛 `LlmError`（非对象 chunk 与既有的"非 JSON 行"一样被跳过）。测试：`test_complete_reports_a_malformed_reply_as_an_llm_error`、`test_complete_stream_reports_a_malformed_chunk_as_an_llm_error`、`test_complete_stream_skips_a_chunk_that_is_not_an_object`。

### L3　工具结果无大小上限，整体进入模型上下文　— 仅记录
- 位置：`src/rag_agent/agent.py:316-318`（`json.dumps(tool_result.structured)`）；`collect_retrieved`（`:406`）对 `sources` 条数也无上限。
- 失败场景：KB 返回很大的 `structured`（或被投毒的文档带超长 snippet）→ 提示超过模型上下文 → 服务器返回 4xx/5xx → `model_error` → 502；成本也随之放大。
- 建议：按字符数截断并标注"已截断"。**会改变模型所见内容，可能影响评测，故未改**；若改，需重跑评测并另写报告。

### L4　`cited_documents` 是子串匹配，可被短文件名/前缀误触发　— 仅记录
- 位置：`src/rag_agent/main.py:80-83`。
- 复现（已实测）：retrieved 含 `faq.md` 与 `1`，答案为 "see myfaq.md and item 12" → `cited_documents == ['faq.md', '1']`。回答里被注入文档诱导写出某个文件名，也会被算作"引用"。字段已在 README 标注为"词法子集"，且 `evaluation/` 不使用该字段（已 grep）。
- 建议：对含 ASCII 文件名要求两侧不是文件名字符，CJK 文件名保持子串匹配；或让模型输出结构化引用。这是对外 API 语义变化，未改。

### L5　工具调用途中 token 被 KB 拒绝（401）被吞为 `transport_error`　— 仅记录
- 位置：`src/rag_agent/agent.py:306-309`。
- 场景：`list_tools` 成功后，token 在 `call_tool` 时失效/被撤销 → `McpError(status=401)` 被转成 "the knowledge base is unavailable" 的工具消息，循环继续；非会话请求可能得到"知识库中没有相关内容"的 200 回答，而不是 401。（带历史的会话因 `enforce_retrieval` 不会接受无检索的回答，是安全的。）
- 建议：对 401/403 向上抛出由 `failure()` 统一处理。会改变停止原因/状态码，未改。

### L6　流式 worker 无取消、队列无界　— 疑似，合并入 M4
- 位置：`main.py:290`。验证见 M4。

### L7　`/docs`、`/openapi.json` 默认开启；422 响应回显 `input` 且不是统一错误信封　— 仅记录
- 实测：`/docs`、`/openapi.json` 返回 200；超长问题的 422 体含 `input`（回显调用者自己发送的内容，约 2 KB）。无跨用户泄漏。
- 建议：生产关闭文档（`FastAPI(docs_url=None, ...)`）；注册 `RequestValidationError` 处理器返回 `{"error":"invalid_request"}` 且不回显输入。

### L8　compose 默认把 8090 发布到所有网卡　— 仅记录
- 位置：`docker-compose.yml:18-19`。服务自己不做认证（依赖 KB 校验 token），默认对局域网可达。
- 建议：`"127.0.0.1:8090:8090"`；需要外部访问时由反向代理终止 TLS 并限流。会改变演示者的访问方式，未改。

## 信息

- **I1 会话隔离（审查通过）**：会话 ID 为 `secrets.token_urlsafe(18)`（144 位）；owner 为带进程随机盐的 HMAC-SHA256，`hmac.compare_digest` 比较，token 本身不存储；未知/过期/他人的会话在 `/ask`、`/ask/stream`、`DELETE` 中响应完全相同（404）。重启即失效，多副本未支持（README 已声明）。
- **I2 token 不外泄（审查通过）**：`McpClient.token` 为 `repr=False`；传输错误 `from None` 且只带异常类名；`login` 不回显凭据；span 属性有白名单；日志只记录 request id、状态码、计数；`failure()` 对客户端只给固定文案。新增测试覆盖 401/502/模型错误/意外异常四条路径在响应体、响应头、SSE、日志中均无 token。
- **I3 身份参数**：身份只来自 `Authorization`；`knowledgeBaseId` 在 `HIDDEN_ARGUMENTS` 中，不展示给模型且被拒绝（已有测试）。注意这是**黑名单**，且 `validate_arguments` 只校验 `string` 类型与 enum，不校验 integer/array/object 及嵌套内容；当前依赖 KB 服务端边界兜底。若 KB 将来新增 `userId`/`tenantId` 类参数，应改为按白名单（只放行 `query` 等已知名字）。
- **I4 循环边界（审查通过）**：`max_turns=4`、`max_tool_calls=3`；被拒绝的调用不计入工具预算但受 `max_turns` 约束（已有测试）；LangGraph 版另有 `recursion_limit`。同一轮内模型可返回任意多个被拒绝的调用，开销很小。无"重复相同调用"去重，由工具预算兜底。
- **I5 容器与依赖**：
  - `Dockerfile` **已**以非 root（uid 10001，`USER agent`）运行，compose 已 `read_only`、`cap_drop: ALL`、`no-new-privileges`；任务书中"以 root 运行"在此仓库不成立。基础镜像 `python:3.12-slim` 只按标签而非 digest 固定。
  - 依赖（`uv.lock`）：fastapi 0.143.0、starlette 1.8.0、uvicorn 0.54.0、httpx 0.28.1、h11 0.16.0、pydantic 2.14.1、langgraph 1.2.15、langsmith 0.14.8、opentelemetry-sdk 1.45.1、urllib3 2.8.0、certifi 2026.7.22。另有传递依赖 `httpx2 2.13.1`（由 langsmith 引入，与 httpx 并存）。
  - **疑似/未能确认**：这些版本晚于我所能核对的漏洞库，且按要求未联网，**无法断言其中是否存在已知漏洞**，也不凭印象列出 CVE。验证方法：`uv export --no-dev --frozen --no-hashes -o /tmp/req.txt && uvx pip-audit -r /tmp/req.txt`（需联网，建议加入 CI 的定时任务或 Dependabot）。
